# Si5351A clock support

The first oscillator driver supports the three-output Si5351A, using CLK0,
CLK1 and CLK2. It is server-private hardware code; it neither implements radio
DSP nor assumes a board frequency plan. `sbitxdsp` remains a separate planned
process. Native and browser clients have no new wire behavior in this change.

## Supported controls

- Each output accepts integer-Hz requests from 8 kHz through 100 MHz, or zero
  to disable it. The chip uses PLLA at a nominal 900 MHz with per-output
  MultiSynth and R dividers. PLL rounding introduces a small frequency error;
  this is not an assertion of exact-Hz hardware accuracy.
- The crystal can be 25 or 27 MHz. Calibration is signed parts per billion:
  positive means the measured reference runs fast. Range: +/-100000 ppb.
- Crystal load: 6, 8 or 10 pF. Output drive: 2, 4, 6 or 8 mA.
- Retuning disables only the selected output while updating its divider.
  It does not reset/reprogram the PLL or other outputs. Changes are not
  phase-continuous or guaranteed glitch-free.
- A bus error or PLL/reference status failure attempts to disable ALL outputs
  and faults the programmer. Release/reclaim is required before tuning again.
  Software cannot confirm output disable when the bus itself has failed.

The equations, register layout and sequencing are based on
[Skyworks AN619, revision 0.8](https://www.skyworksinc.com/-/media/Skyworks/SL/documents/public/application-notes/AN619.pdf).
The implementation deliberately limits its range; it does not support CLK3..7,
Si5351B/C features, the 16-QFN register variant, quadrature phase programming,
external clock references, or outputs above 100 MHz.

## Register a device in rrserver

```ini
[general]
hardware.si5351=lo

[si5351:lo]
; Example only: use the actual kernel adapter connected to your oscillator.
bus=/dev/i2c-3
address=0x60
crystal-hz=25000000
correction-ppb=0
load-pf=10
drive-ma=2
```

This creates an `i2c-bus` parent and `si5351:lo` oscillator in the hardware
registry. Registration resolves the adapter path but does not access the chip
or enable clocks. Duplicate bus/address mappings are rejected, including
symlink aliases. Configuration changes require restart. Invalid settings or
missing adapter paths fail server initialization with a diagnostic.

A backend claims the entire device through `rr_hardware_claim()`, then uses
`rr_si5351_tune(device, output, hz)` from its owning worker. Claim initializes
the chip with all outputs disabled. Release disables all outputs before
closing the adapter. A failed release retains the lease. The current internal
backend does not bind this device or translate dial frequencies automatically.

The Linux adapter uses `/dev/i2c-*` and atomic `I2C_RDWR` transactions, including
repeated-start register reads. It checks adapter capabilities and refuses a
kernel-owned I2C address rather than using `I2C_SLAVE_FORCE`. Different chips
can use the same kernel adapter. Registry exclusivity is within rrserver;
other userspace applications must relinquish the chip before testing.
Status polling is bounded to 200 attempts with approximately 1 ms waits;
individual kernel I2C calls still depend on the adapter driver's timeout.

## Bring-up without a radio backend

Build the server and diagnostic tool:

```sh
make -j4 bin/rrserver bin/rr-si5351
```

Preview settings without opening any device:

```sh
./bin/rr-si5351 --crystal-hz 25000000 --clk0 10000000 --clk2 7100000
```

Apply a known test clock on the target hardware:

```sh
./bin/rr-si5351 --apply --bus /dev/i2c-3 --crystal-hz 25000000 --clk0 10000000
```

These are example clock frequencies, not an sBitx operating profile. Confirm
the bus, crystal, output wiring and load capacitance against the board. Stop
stock sBitx software or any other process controlling that oscillator first.
The account needs read/write permission on the I2C adapter. No GPIO library or
additional I2C userspace SDK is required for this driver.

The tool previews by default. With `--apply` it disables every output during
initialization, enables the requested clocks, and waits. Enter, EOF, SIGINT
or SIGTERM disables the clocks and closes the device. A forced kill or power
loss cannot perform cleanup. Keep the transmitter inhibited during oscillator
bring-up; no PTT/filter/PA sequencing is implemented here.

The tool is included in the `rustyrig-server` Debian package. A Pi 4 can compile
RustyRig, but it does not need a compiler to run packaged binaries. Build on a
matching ARM Debian system/builder, or configure a cross-toolchain and target
sysroot. Match the Pi's installed userspace architecture (`dpkg --print-architecture`:
arm64 or armhf); ordinary x86-64 binaries from a desktop will not run on it.
Copy/install the matching RustyRig libraries and runtime dependencies along
with the executables, preferably using the Debian packages. Cross-compilation
and actual Pi operation have not been validated by the hardware-free checks.

## Checks

```sh
bash tests/with-xvfb.sh bash rrserver/tests/test_si5351.sh
```

Checks cover known register vectors, decoded frequency error across both
crystals and calibration limits, output independence, invalid requests,
initialization/retune write failures, read failure and status timeout, plus
configuration loading, duplicate addresses and unavailable adapters. No physical I2C
transactions are needed. The root component runner discovers this wrapper.
